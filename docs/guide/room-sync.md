## Recipes

Where a step says "the typecheck asks", `bun run typecheck` fails until it is done.

- A room message: its payload in `Payloads` and its `DEFS` entry in `src/core/protocol.ts` (`gmOnly`, `ownSheet` when it speaks for the hunter in its `by` so the server takes it only from that hunter's phone, and a bounded reader), and its applier in `APPLIERS` (`once: true` with a `land` if it changes a hunter: a pure step on the save, the change made with core steps such as `grant` and `sheetEdit` (`src/core/hunter/grant.ts`), and a `tell` run only when the step was written with the event's id; `null` if a player's phone does nothing); the typecheck asks for both. Post it with `app.api.sync.post(app.api.sync.event(type, body))`: the outbox keeps it until the room takes it, and nothing sends once (a lint test; a browser test that replays a copy posts it too). Its valid payload in `VALID` (`tests/protocol.test.ts`) and a case per bound; a GM-only refusal in `tests/server-rooms.test.ts`; a message only the GM and the hunters it names may get is `sealed` in its `DEFS` entry (`servedTo`), with a case in `tests/server-rooms.test.ts`; one that changes a hunter is a GM move in `tests/models/room-world.ts` (the exhaustive run keeps one move per way of posting, so a message posted as another is skipped there and played by the random walks). A player's move in the GM's fight is `step`, `cast` or `pass` (End turn) (`ownSheet`, applier `null`): the GM's `combat.js` takes it only when `onTurn` (`protocol.ts`) says it is that hunter's turn at the doc's `at`, so a replay or a stale tap changes nothing; the player's `table.js` holds the turn from a posted move until a doc of another `at` arrives or the room refuses that move (`hold`, `canAct`, the `sync:outbox` event), so a second tap is not sent stale; the fight answers a player's hunter with `vitals` (totals).
- A message that ends another once: its id is made from the other's (`endIdOf` in `src/core/ids.ts`) and made by `endEvent`; its reader refuses any other id and every other reader refuses an id of that form (`isEndId`), so the room keeps the first; each phone reads it by a fold guarded by a record of its own (`offersSeen` in `src/core/trade/offer.ts`), never by the applied ring. A tap that posts the same end again puts a refused letter of its id away first.
- A link state or reply: `Link` or `LinkEvent` (with its `gen`) in `src/core/sync/link.ts`, handled in `step`; leave a state through `leaving(...)`. Tests in `tests/link.test.ts` and the reply in `REPLIES` (`tests/models/sync-world.ts`). `sync.ts` raises it in `ask` and carries out effects in `runLink`. Pill words in `room-pill.ts` and `STATE` in `room.js`, listed in `docs/agent-handoff/copy-tasks.md`; its arrow in `scripts/charts/link.ts`.
- A use the GM should hear of: the player's phone calls `app.api.uses.report` (`uses.js`); on the GM's phone a line is written through `app.api.sync.once(eid, write)` so a replay writes nothing, with kind `use` so "Reward uses" counts it.
- A rule that differs by where the phone sits: a function in core that takes the `Seat` (`src/core/role.ts`: `alone`, `gm`, `player`) as an argument, with a case per seat in its test; the view passes `app.seat()`. A view never tests the room as a yes or no nor puts `isGM()` beside it (the lint "a view asks app.seat() whether this phone is in a room, and as what"); `app.isGM()` alone is for GM tools, which a GM alone uses too.

## Build handshake

Every `/api/rooms...` request carries the build id in `X-Hunter-Build`; the server answers another build with `426 { error: 'upgrade', build }` and the app reloads once, after the new build's service worker has cached every file and taken over, or at once when none installs (the app update's machine in `src/core/upgrade.ts`, run by `src/edge/upgrade.ts`). A change to the room wire format needs no version number. A test that calls the room API sends the header: `roomHeaders(page)` in `tests/e2e/helpers.ts`, or `buildApp()` in a bun test (`tests/server-handshake.test.ts`).
