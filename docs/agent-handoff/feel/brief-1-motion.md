## Steps

1. **Inventory and subtract.** List every transition, animation, keyframe and timed `setTimeout` in `public/app.css` and `src/views/` today (a table in `docs/agent-handoff/feel/notes-1-motion.md`: where, what it animates, its time, whether it animates a layout property). Delete the ones that animate layout properties (`width`, `height`, `top`, `left`, `margin`, `padding`, `box-shadow` on large areas) or duplicate each other; the rest move onto the system in step 3. Commit.
2. **The system.** Tokens in `public/app.css` on `:root`: three durations (`--t-fast` about 120 ms for a press or a chip, `--t-base` about 200 ms for a window, a toast, a slide, `--t-slow` about 320 ms for a bar or a number), two easings (one that leaves fast and settles for things arriving, one that leaves gently for things going) and one overshoot for a pop; each with a one-line reason as a comment. `src/views/motion.ts` (typed, the one home): a small set of named moves, each a function that takes an element and returns when it is done or was interrupted, built on the Web Animations API and CSS classes, reading the tokens (never a literal time): `enter`, `leave`, `press` (pure CSS where it can be: `:active` must answer in the same frame), `pop`, `shake`, `flash`, `slideTo` (FLIP: measure, move with `transform`), `countTo(el, from, to, format)` (a number rolling to its value, tabular numerals so the width does not jump), `fillTo(bar, fraction)` (a bar by `transform: scaleX`, with an optional trailing ghost for a loss), `burst(kind, at)` with a table of kinds (colour, count, spread, life) drawn from a pool on one layer, and `progress(el, fraction | null)` (a real fraction shown as a bar and a whole percentage, or null for "waiting" as a quiet pulse with words). Rules inside the module: only `transform` and `opacity` are animated; an element already moving is taken over, not queued; under `prefers-reduced-motion: reduce` every move ends at once in its final state and `burst` draws nothing; nothing here blocks input or delays a command (a view never awaits a move before sending). Unit tests where there is logic to test without a browser (the easing of `countTo` reaching exactly `to`, the pool never growing past its cap, the reduced-motion path). `bun run typecheck`, `bun run test`. Commit.
3. **Guards.** In `tests/lint.test.ts`, each named as the rule with why and what to do instead: no `transition` or `animation` in `public/app.css` or a view with a literal time (only the tokens); no `@keyframes` or `.animate(` outside `motion.ts` and the block of `app.css` it owns; no layout property in a `transition`; `src/core` and `src/edge` do not import `motion.ts`. Then `tests/e2e/feel.e2e.ts`, the lag test, with the CPU slowed four times through the Chrome DevTools protocol (`Emulation.setCPUThrottlingRate`) on a 390 px phone: (a) a GM plays one turn of a seeded fight (a use on a target, then the next turn), (b) a maker opens from the Make row, (c) the sheet scrolls; during each, frame times come from `requestAnimationFrame` deltas recorded in the page and long tasks from a `PerformanceObserver`; the test fails if any frame is over 50 ms or a tap takes over 100 ms to show its first response (the pressed state or the window's first frame). The test must fail when you add a 80 ms busy loop to a tap handler (check once, say so). It runs with animations on (find how `device()` or the config turns them off for other tests and leave those as they are). Commit.

## Rules

- No dependency. No animation library. No sound.
- A view computes no fight number and awaits no animation before it sends a command: an animation shows a result that already happened.
- No test is skipped, loosened or given a retry. No fixed wait added to a test to let an animation finish; wait on what the player sees.
- If a step cannot be done as written, do the nearest thing that keeps the rule in bold under "Why", and put the difference at the top of the notes.
- Plain whole sentences in notes; comments only for a why.
