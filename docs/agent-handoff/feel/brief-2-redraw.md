## Why (the owner's goal)

the owner, the owner and GM, whose players are on phones: "I don't want them to be laggy, this site should not be laggy." The lag test of feel unit 1, with the CPU slowed four times, measured a worst frame of 67 ms (median of ten runs, 50 to 100) during a fight turn and 33 ms (17 to 50) opening a maker, and showed with motion cut that the cost is the app's own work: the fight rebuilds its whole card and turn order on every change, and the item maker builds its whole form inside the tap. The limits were set from those measurements (133 ms and 83 ms). That holds the symptom. This unit removes the cause and brings both limits to 50 ms. A battle map is built on the fight screen next, so the way the fight screen updates must be right before then.

## Steps

1. **Measure before you change** (benchmark-checklist). A profile of one fight turn on the GM's phone and on a player's phone at four times slowdown (Chrome DevTools protocol `Profiler` or a performance trace through Playwright): where the time of the worst frame goes, by function, as a table in `docs/agent-handoff/feel/notes-2-redraw.md` with the run count. Name what you expect to gain from each change before you make it. Commit the notes.
2. **Choose the way a fight screen updates, from two or three written options** (exhaust-the-design-space), in the notes, half a page: for example (a) keyed patching: each row and card has a key, a render gives a description (the model `fight-view.ts` already returns: `order`, `cardOf`), and one small function updates only the nodes whose description changed; (b) fine-grained setters per field of a card; (c) keep the full rebuild but move it off the tap's frame. Judge each by: frames on the slowed phone, how a new thing on a card is added (the owner adds a lot: it must stay one place), how motion finds what changed (`fillTo`, `countTo`, `slideTo` need the old node to still be there, which a rebuild destroys), and how the map will use it. The lead leans to (a) with the description as plain data from `fight-view.ts`, because the description is already the screen's model and a diff of two descriptions is a pure function that can be unit tested; overturn that only with a measurement. No dependency, no framework: one small module (`src/views/patch.ts` or the like) with tests.
3. **Build it and move the fight on it**: the GM's fight screen (`combat.js`: the order ahead, the card, the bar) and the player's HUD (`table.js`). A change to one row touches that row's nodes only. The moves of `motion.ts` now act on nodes that persist, so remove any workaround feel unit 1 needed to animate across a rebuild (say which). Core is not touched except to give `fight-view.ts` a description shape that diffs well, with its tests. Commit when `combat-turns.e2e.ts`, `table-session.e2e.ts`, `table-turn.e2e.ts`, `used.e2e.ts`, `fight-vitals.e2e.ts`, `layout.e2e.ts` and `feel.e2e.ts` pass.
4. **The makers**: opening a maker shows its window in the tap's frame and builds the heavy part of the form after (the next frame or two), with the form's first fields ready at once, so nothing a GM can tap is missing when they can see it (a test taps the first field the moment the window is visible). ## Rules

- No dependency, no framework. The smallest module that does it, with unit tests for the pure part.
- A view computes no fight number (the lint tests hold it). What a card shows comes from `fight-view.ts`.
- No test skipped, loosened or given a retry; no fixed wait added.
- Behaviour a player or GM sees does not change, except that it is faster. If a screen's words or order change, that is a bug in this unit.
- Plain whole sentences in notes; comments only for a why.
