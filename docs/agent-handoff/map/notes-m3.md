## Step 2: three ways to draw the map

Judged on a 390 px phone at 4x CPU with twenty tokens and a shaded area of a hundred tiles.

- **(a) Elements in one transformed layer.** A `.mp-world` element holds the tiles' shading, the way and the tokens, each placed by `transform: translate()` in tile units times a fixed tile size (40 px); pan and pinch change only the world's own `transform` (compositor only, no layout). A token is a `<button>` with an `aria-label` (its name, HP or band, "your turn"), so it is a tap target and is read out. An area is drawn as one element per tile in a second layer (`.mp-area`), keyed by tile and patched with `keyed` and `bind` (patch.ts), so a new area writes only the tiles that changed; at a hundred tiles that is a hundred small absolutely placed `<i>`s, which style and lay out once (they never affect each other's layout: `contain: strict` on the layer). `motion.ts` moves a token as it moves any element (a `transform` from its old place), and its bursts find the token by its box. Zoomed in it stays sharp: the layer is re-rastered when the gesture ends (`will-change` is set only while a gesture runs). Walls, zones and fog are more elements in more layers under the tokens, drawn from the same `terrain` list.
- **(b) One SVG.** Tokens as `<g>` with `<circle>` rings, areas as one `<path>` per shade built from the tile set (merged squares), pan and zoom as the `viewBox` or a `transform` on a `<g>`. Sharp at every zoom with no re-raster, and an area is one node. But a change of `viewBox` re-renders the whole SVG on the main thread every frame of a pan (not the compositor), `motion.ts` animates elements by CSS `transform`, which on SVG children is supported but each moving `<g>` repaints the SVG; and a token as a button with a name needs `role` and `tabindex` on a `<g>`, with focus rings drawn by hand.
- **(c) A canvas.** The cheapest to draw twenty tokens and a hundred tiles in one call, and a pan is a redraw of one bitmap. But nothing on it is an element: no tap target, no name for a screen reader, no `motion.ts` move (a token's slide would be a second animation loop of its own, against the rule that every move is in `motion.ts`), and every frame of a pan is a full redraw on the main thread, which at 4x is the one budget this unit must hold.

Chosen: (a), as the lead leaned. Reading decided it; no sketch was needed: the pan and pinch of (a) are a single `transform` on one element, which is the only thing that keeps a gesture off the main thread, and (b) and (c) both redraw on the main thread during a pan. The measured frames are in step 6. One change from the lead's lean: the area is one element per tile, not merged shapes. Merged outlines need a polygon per region worked out in the view (a sum of squares) or an SVG path; a tile element is what the scene already gives, `keyed` patches it, and the soft edge comes from each tile's rounded corners and a slight blur on the layer. If step 6 shows a hundred tiles bound a frame, the merged path is the next thing to try.
