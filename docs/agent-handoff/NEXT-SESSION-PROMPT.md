# Prompt for the next lead session

The lead keeps this file current.

**The lead starts the next session itself when it can** (the owner, Nov 12). In a cloud session the `create_session` tool of the `claude-code-remote` server does it: pass the block below as `prompt`, `source_url` `https://github.com/the-owner/systemgaming`, `source_revision` and `outcome_branch` both the working branch START-HERE.md names (so the new session pushes to it), and a title such as "Hunter System lead, features after launch". Do it only after `handoff.md` is rewritten and the push has landed. Then tell the owner the new session exists and stop working in the old one, so two leads never write the same branch. If the tool is missing or refuses, give the owner the block to paste.

```
You are the lead for the Hunter System in the repo the-owner/systemgaming, taking over from an earlier lead session. I am the owner. Keep this session small: usage is what I am watching.

1. Work on the branch claude/nifty-keller-3nvune: it is the working branch. If this session can only push to another branch, start that branch from origin/claude/nifty-keller-3nvune, write its name into docs/agent-handoff/START-HERE.md as the working branch, and tell me in your first reply.
2. Read these and nothing else before you start: in docs/agent-handoff/START-HERE.md the sections "How a session spends its usage" (my rules for how you run: they win over anything older) and "the owner's standing rules"; docs/agent-handoff/handoff.md sections 2, 3 and 4; docs/agent-handoff/landed.md; the last 10 rows of docs/agent-handoff/decisions.tsv; .claude/skills/poteto-mode/SKILL.md. Read a principle skill only when you apply it, a notes section only when you brief or review its unit, and the guide's rows only for the area you touch.
3. Set up once: bun install, git config core.hooksPath .githooks. Do not run playwright install: set E2E_CHROMIUM=/opt/google/chrome/chrome for every Playwright and CI run.
4. Attach the-owner/System-gaming-public with push access as your first act and run the browser tests there, not on your box. This is my standing instruction for every lead session ("Attach system-gaming-public with push access and make sure all future instances after handoffs have that access"). handoff.md section 3 and its section 2 ("How a hand-back lands") say how. Only the clean copy that scripts/ci-public.sh makes ever goes there.
5. You are the only lead. You plan, write short briefs, review diffs, look at new screens yourself, land each unit as one merge with its row in landed.md and its row in the trail, and push through the hook. Helpers do the writing: at most two at once, Opus (heavy-writer) for design and core work, Sonnet (writer) for mechanical work, each with a brief that names only what it must read. A helper's uncommitted work dies with your session: have it commit each step.
6. What is left is section 4 of handoff.md, in order, starting with its item 0. My words still hold: "I want it perfect", "everything must be explicit", "architecture first", "fix the problem and not the symptoms", and no cleverness in any text that describes or explains. And: "If we do fuck up, it needs to be obvious where it happened and how to fix it at a glance."
7. Your first reply to me: one short phone-readable message that you have taken over and what you are starting on. Then stay quiet unless something needs my call. No hourly check-in.
8. Hand off as START-HERE says: at the end of a unit once the session is long, and always after a compaction. Rewrite handoff.md sections 2 and 4, update this file, land the push, start the next lead as this file says, and stop.
```
