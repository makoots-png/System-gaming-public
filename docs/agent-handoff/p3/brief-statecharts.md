## Why (the owner's goal)

the owner wants no implicit state machines and wants both a person and an AI agent to see at a glance how each machine moves. The machines are now explicit in code: the fight (`src/core/combat/encounter.ts`), the gate (`src/core/gates/gate.ts`), the room link and the sheet push (`src/core/sync/link.ts`, `push.ts`, with `connection.ts` for what the pill shows). More are coming (a hunter's life, the penalty, the job chain). A chart drawn by hand goes stale the day someone adds a state. The owner decided earlier not to keep a second formal model (TLA+) beside the code. So the charts are generated by walking the real reducers and tables, and a test keeps them current.

## What to build

1. `scripts/statecharts.ts`, run as `bun scripts/statecharts.ts` (add `"charts"` to `package.json`). A small generic walker: given a machine's start states, a finite list of events to try, its `reduce` (or `transition`) and a view, it explores breadth-first every reachable state, maps each to a chart state through the view, merges model states that share a label, and emits Mermaid `stateDiagram-v2` text. The existing model tests already do such walks (`tests/sync-model.test.ts`, `tests/encounter-model.test.ts`, the sequence walk in `tests/gate.test.ts`): reuse their event alphabets and state keys by importing or by moving the shared part into a small module both use. Do not write a second, different alphabet for the same machine.
2. One view per machine in `scripts/charts/`, following the skill's view idea:
   - `state(s)`: a string for a flat chart, an array for parent states (for example `['In a room', 'Reconnecting']`), an object for parallel regions (link and push side by side).
   - `step(event, from, to)`: the arrow's label as the player or GM sees it happen ("you tap Leave", "the room answers", "the GM clears the gate"), or `null` to hide a step. Follow the skill's rules on hiding: all steps of an arrow or none, never hide a path to a state, say in the output what is hidden.
   - a title and a one-paragraph note under the chart saying what the model leaves out.
   Write labels with no variable names and no code words. Aim for 20 arrows or fewer per chart; where a machine is bigger (the link), use parent states and, if needed, two charts (the link alone, then link and push as regions at a coarser grain).
3. `docs/state-machines.md`, generated (`--write`), with `--check` for the test. One section per machine: the chart, the note, and a table "where it lives" (the file with the union, the function that changes it, the dispatcher or view that calls it, the test to copy, the AGENTS.md recipe). Stable output, no timestamps.
4. `tests/statecharts.test.ts`: the committed file is current; every state of each machine's union appears in its chart under some label (derive the list of states from the walk and from the union's discriminant values, so a new variant with no label fails); no chart has an unreachable chart state.
5. Look at each chart rendered (write the Mermaid to a scratch HTML page and open it with the Chromium at /opt/pw-browsers/chromium through Playwright, screenshot it, read the screenshot) and fix what a reader would trip on: crossing clutter, a label that needs the code to understand, an arrow that seems to go nowhere. Record in the notes one thing you changed per chart after looking. If Mermaid cannot be loaded offline here, say so and check the text by hand instead; do not add a dependency or a CDN link to the repo.
6. `AGENTS.md`: a short section "Seeing how a machine moves" (the file, the command, that a new machine adds a view in `scripts/charts/`), and add "its chart view" as a step of the recipes that add a state or event (combat command, gate status or event, link state or reply).
