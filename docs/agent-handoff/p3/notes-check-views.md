## Step 2: sort and decide

Principles that changed a choice: `principle-type-system-discipline` (fix the typed side where the view shows the contract is wider, rather than bend the view), `principle-laziness-protocol` (one declaration file for the DOM instead of ~330 casts).

Of the 572:
- (c) DOM noise, 338: TS2339 on `Element` (182), `EventTarget` (137), `HTMLElement` (8), `Event` (5), plus `window.webkitAudioContext`, `window.hunterApp`, `ui.h` answering `Element`, form controls read by name (`form.tname`). lib.dom answers `Element` for `querySelector`/`closest` and `EventTarget` for `e.target`; none of it touches a contract.
- Config artifacts, 4: `__BUILD__` (types/ was not in the include) and two `'drop' in` narrowings in sync.ts that only fail under the loose options.
- The app object, 7 (app.js): `layout` and `keys` added after the literal, the literal not typed as `App`.
- Window and prompt options, 13 (b): ui.js's `system`, `promptNum` signatures were inferred from defaults (an action needed `cancel`; `promptNum` had no `min`/`max`).
- The rest, about 210, are calls into typed code. Sampled and sorted:
  - (b) `AppApi` narrower than the module: `bestiary.toCombatant` takes an id or a monster (gates.js passes ids); `loadouts.save` answers a string, `loadouts.swap` an object, `build.respec` an object, `inventory.sell` a number (declared boolean); `hunter.derived` has `checkBonus`, `atkMod` (typed as `unknown` in a record); `dice.roll` answers `expr`; `dice.check`, `hunter.gainXP`, `bestiary.statBlock` answer `unknown` and the views read fields; `effects.effectsOf` takes a second argument.
  - narrowing the compiler cannot see: `isRemote(c)` and similar helpers without a type predicate (Combatant `.remote`, `.hp`: 13), `Encounter` `.round` read without a `running` check (5), table.js reading a `RollPayload | QuestUpdatePayload` without checking the event type (10), `app.api.sync || {}` giving `SyncApi | {}` (32 `on type '{}'`).
  - JS idioms that run fine: `isNaN(date)`, `date - number`, `setAttribute(name, number)`, `textContent = number`.
  - (a) candidates still being checked: see step 3.

Decision:
- TS2339 stays on: it is the check that finds a member that does not exist on an API, a payload or a save type, and it also produced all 338 DOM errors. The DOM part is fixed at its source in one place: `types/views/dom.d.ts`, read only by `tsconfig.views.json` (the main config excludes `types/views`). It adds overloads so a lookup (`querySelector`, `querySelectorAll`, `closest`, `ui.h`, `ui.$`) answers a `ViewElement` (an HTML element with the form-control fields the views read) and a listener added with a string type hears a `ViewEvent` (keyboard and pointer fields, a `ViewElement` target). It does not use `any`. It loosens nothing for the TypeScript files.
- Off in the config, because they only fight untyped DOM code: `strict`, `noImplicitAny`, `strictNullChecks` (retried in step 5), `exactOptionalPropertyTypes` (needs strictNullChecks). Everything else of the main config stays (`noUncheckedIndexedAccess` has no effect without strictNullChecks).
- ui.js got JSDoc types for `h`, `$`, `toast`, `system` (`SystemWindow`, `SystemAction`), `confirm`, `promptNum`, `promptText`: it is the typed side of every window a view opens.
- After this: 344 errors, 98 DOM left (expandos such as `el._render`, `document.activeElement`, `children`), 246 on contracts.
- Commit: step 2, types/views/dom.d.ts, ui.js window types, main config excludes types/views.

## Step 5: tighten

- `strictNullChecks` on for the views: 967 errors. By what is possibly null (a script over the error columns, rough): 303 DOM lookups (`querySelector`, `closest`, form controls, `$()`), about 155 more on values that come from those lookups, 156 on an `app.api` member (`api` is `Partial<AppApi>` because a module may use only the modules registered before it; at run time every one is registered), 41 index reads (`noUncheckedIndexedAccess` comes with it), 21 store or list lookups that can miss, and about 290 of other kinds (assignments of null, overloads). Mostly DOM and the API's registration order, not contract mistakes: left off.
- `noImplicitAny` on: 1633 errors, 929 of them TS7006 on parameters of the views' own helpers (`h`, `e`, `c`, `x`, `v`, `n`). The callbacks that receive typed values are already inferred: `store.update<T>(fn: (save: Save) => T)` and `app.on<K>(name, fn: (payload: AppEvents[K]) => void)` are generic, and only 5 of the 929 sit in such a callback (forge.js's `store()` alias and starter.js before commit 5). Left off.
- Commit 8: forge.js kept the app in a module-level `let A = null` (so `any`: none of its app calls were checked) and ui.js its store the same way; both typed now. It found forge.js reading `o.dice` on any op: it reads it through `isNumOp` now (same four ops as its local `NUM`).
