## Why (the owner's goal)

"We're optimizing for customizability. The ability to make custom abilities, status effects, custom rewards, items, enemies, etc... and ways to notify me when players have used rewards." He will add content kinds and fields often. So each kind gets one parser every path uses, and one home in the save. This unit builds that for what exists today. Later units add skills, rewards and the makers on top of it.

## Steps

Each step: tests first, then the change, then `bun run test`, then commit.

1. **Delete dead weight.** `lootTables` in the save (no writer; `rollLoot` reads it: remove that read, keeping the roll by rank it falls back to). `statusDefs` on a `Monster` (no reader; remove the auto-add write in `bestiary.js`). The shadow `abilities` read in `combat.js` (a `Shadow` has none). The fallback `statusDialog` in `gm.js` if `forge.status` is always registered (check `MODULES`; if it can be missing, leave it and say why).
2. **`parseItem` in core** (put it beside `itemOf` in `src/core/registry/items.ts`, or a new `src/core/item.ts` if imports force it; say which and why in the notes). It turns unknown input into an `Item` or `ItemTemplate` or null, with one set of bounds: qty 1 to 9999, heal, mp and fatigue as `inventory.js` `clean` has them (heal up to 99,999), value, dice text, the nine bonuses, effects through `sanitizeOps`. Tests in `tests/items.test.ts`: round trip of every built-in through it unchanged, hostile input (wrong types, huge numbers, extra keys dropped, a bad effect dropped), the bounds. Then migrate the four callers and delete them: `fixItem` (`save.ts`), `givenItem` (`protocol.ts`), `clean` (`inventory.js`), `cleanItem` (`quests.js`). A room message keeps its own count bound (20 items) and uses `parseItem` for each. The quest reward repair in `save.ts` uses it too. Keep every existing test green or update it to the one set of bounds, and list each changed expectation in the notes.
3. **An item's ops resolve at its rarity.** Export from `src/core/combat/status.ts` the one function that turns ops with `tiers` into flat ops at a tier (the one `statusDef` uses; do not write a second). Item use (`src/core/.../effects.ts` and `src/views/effects.js`) and `inventory.bonuses` (worn mods) call it with the item's rarity tier, so an op with `tiers` no longer rolls 0 and a worn mod with `tiers` no longer adds `undefined`. A worn `check` mod: find what reads a status's `check` mod on the sheet and make a worn item's count the same way, or, if nothing on the sheet uses `check`, leave it and say so. Tests: a potion whose heal has `tiers` heals the rarity's value; a worn ring with `tiers` on `ac` adds the rarity's value; a `pct` heal on use heals that percent of the user's max HP.
4. **The Loot Forge keeps what it cannot show.** `rowsFromEffects` in `loot.js` drops a heal or damage with `tiers` or `pct` and turns a mod with `tiers` into +1 on Edit. Make Edit and Save keep such ops untouched (as the Status dialog keeps ops its chips cannot show). A browser test in an existing item or forge e2e file: put an item with a `tiers` op in the library through the store, open Edit, save, read it back unchanged.
5. **`library.statuses`.** The type in `save.ts` (`library: { items, statuses }`, `statuses: Record<string, StatusDef>`, at most 200 keys, each key a slug of at most 40 characters, each def through `sanitizeDef`). At load, entries under `rulesOverrides.conditions` move into `library.statuses` (through the parser) and the key is removed from the overrides. `rulesOf` merges `library.statuses` over the built-in `conditions`. `forge.js` reads and writes `library.statuses`; the `custom: true` mark goes (an entry is custom when its key is not a built-in key, an override when it is). The dialog's Edit lists built-ins too: saving one writes an override under the same key, and Delete on an override restores the built-in (the button says "Reset" for an override; add the word to `docs/agent-handoff/copy-tasks.md`). The GM's "Reset rules" keeps the library. Tests in `tests/save.test.ts` (the move at load, hostile entries dropped, the cap), `tests/rules.test.ts` (the merge, an override of a built-in, a custom key) and `tests/status.test.ts` if a lookup changes. Browser: `tests/e2e/` already has status dialog tests; keep them green and add one: a GM edits Poisoned's name in the dialog, sees the new name on a combat card, resets it, sees the old name.
6. **`parseOverrides` in core** (`src/core/rules.ts`). Move `validate` out of `gm.js` into a pure function that takes unknown input and answers the cleaned overrides plus a list of what it refused (path and reason). It refuses `conditions` ("statuses are made in the Status dialog"; copy-tasks). The save repair calls it at load, so a damaged override no longer reaches `rulesOf`. The rules editor calls the same function and shows the refusals as it does today. `gmTables` and `gateNames` keep working. Tests in `tests/rules.test.ts`: a valid override survives, an unknown key is refused, a wrong type is refused, `conditions` is refused, and every override the roll tables and the Build panel write passes.
7. **`parseMonster` in core** (`src/core/registry/monsters.ts`): from `bestiary.js` `clean` and the repair lines in `save.ts`, one function, both callers migrated. Add `elite: boolean` to the bounds if it is not already kept. Tests in `tests/monsters.test.ts`: every seed made into a monster passes unchanged; hostile input.
8. **A lint test** in `tests/lint.test.ts`: only `parseItem` builds an `Item` from unknown input. Write it the way the file's other one-writer rules are written (for example: no function named `clean`, `cleanItem`, `fixItem` or `givenItem`, and no view reads `rulesOverrides.conditions`). Its message says what to call instead.
9. `bun run test`, `bun run deps -- --write`, `bun run charts`, then the browser files that touch what changed: find them with `grep -l "forge\|library\|inventory\|bestiary\|shop\|Rules editor" tests/e2e/*.e2e.ts` and run each. Then `AGENTS.md`: update "Where things live" (a row for "What a custom status, item or monster may hold": the parsers) and the Item, Status and Monster recipes where a path or a name changed. Keep it short.
