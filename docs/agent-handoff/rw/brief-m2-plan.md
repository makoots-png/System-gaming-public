## Why (the owner's goal)

the owner is the GM of a tabletop game played on phones. The reworked fight (turns from speed, eight stats, Armor and Resist, places on a grid) exists as tested pure code beside the old fight, and no screen uses it yet. Milestone 2 moves the app onto it and deletes the old fight, the six stats and AC in the same wave, so nothing is left side by side. His bar: "Idc if it's big changes so long as the architecture remains ROCK solid", "everything is defined, easy to find", "No implicit state machines anywhere", and a view only draws and sends taps. The lead writes each unit's brief from your plan without opening the code, and Opus helpers execute the units one after another in this tree, so the plan must be exact.

## The constraints the plan must fit

- Every push runs the whole CI through a hook, and nothing is pushed red. The wave cannot be green in the middle (the stat keys change under every view at once), so it is one run of local commits with one push at its end. The plan's job is to make that run as short and as safely ordered as it can be: each unit ends in a check that is green for what the unit owns (for example `bun run typecheck` and the named `bun test` files and named browser files), and says exactly which other checks are expected red after it and which later unit turns each green again. No test is skipped, marked `fixme` or deleted to get green; a test of deleted behaviour is deleted with the behaviour, in the unit that deletes it, and a test of kept behaviour is moved to the new code in the unit that moves the behaviour.
- A unit is at most about 90 minutes for one Opus helper and touches a set of files no other unit of the same step touches. Say which units could run at the same time in separate worktrees (new files only) and which must be in sequence.
- Milestone 2 is the wiring only. The map view (a grid drawn with tokens and tap to move) is milestone 3, the makers for the new ops and the typed formula field are milestone 4, intent, threat, stagger, shield and channel on the screens are milestone 5. In milestone 2 a fight runs on `fight.ts` with default places and no map drawn: the screen shows the order ahead, the cards, a use with its target picker, the outcomes, and a move as a plain "step toward / away" or distance control only if a fight cannot be played without it (say which, with the reason). Abilities that need a place aim at a combatant's place.
- A new campaign: `schema: 4`, no carry-over from schema 3 (the old save is kept in the backups with a plain message, as a text that is not a save is today).

## What the plan holds

1. **The target, in one page.** After the wave: which module owns what (the new rows of `AGENTS.md`'s "Where things live"), what a `Hunter` in the save holds (every field, with the fields that go), what the room doc and each fight message carry, what each view imports from core. Written as it will be, not as a diff.
2. **Every caller of what dies.** A table: each old export that is deleted (`encounter.ts`, `encounter-types.ts`, `encounter-parse.ts`, `use.ts`, `status.ts`, `ability.ts` if it goes, `mod`, the six `STAT_KEYS`, `PERK_KEYS`' `ac`, `rankTable`'s columns, `derived()`, `bonuses`, each number of inventory 6.2), every file and line that reads it, and what that reader uses instead. Built with grep and `bun run deps -- <name>`; say the commands.
3. **Content.** For the registries (monsters' `SEEDS`, items, paths and perks, skills, statuses, jobs' bonuses, titles, starter hunters): how each entry is restated on the new rules (which archetype and kind a monster seed becomes, how an item's AC bonus becomes armor and weight by slot, how a perk's stat keys map, how a built-in skill becomes a typed `Ability` of a kind, how each built-in status becomes new ops), as a rule a helper can apply to every entry, with five worked entries of each registry and any entry the rule does not fit listed by name with your call. This is where balance content is decided: use the design's kits and kinds, and keep each registry's per-entry test idea.
4. **The units, in order.** For each: its name, the files it creates, changes and deletes, the tests it moves, rewrites or deletes (by file, with counts), its check (exact commands), what is red after it and until which unit, what it must read, the principle rows of `rw/principles.md` that bite, and the traps (from the inventory's 6.3 and the notes). Include the unit that adds the lint tests ("no view computes or rolls a fight number", "only the fight changes a place, HP, shield, stagger, channel, threat or a fight status", "nothing imports the deleted modules"), the unit that updates `AGENTS.md`, the dependency map and the charts, and the last unit that runs everything and fixes what is left. Put first whatever shortens the red time (for example: anything that can land green before the wave starts, such as new pure code the wave will need, a `schema: 4` parser beside the old one, new e2e helpers).
5. **The browser tests.** For each `tests/e2e/*.e2e.ts` file: how many tests survive unchanged, how many are rewritten for the new fight or stats and in which unit, how many are deleted with their behaviour. And what `scripts/ui-shots.ts` needs.
6. **Risks.** The five things most likely to go wrong in the wave and what the plan does about each, and what you could not determine by reading.
