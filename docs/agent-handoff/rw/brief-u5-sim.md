## Why (the owner's goal)

the owner is the GM of a tabletop game played on phones. He reworked the fight on paper with the lead and said: "I want to make it so that some classes will naturally beat others in a rock paper scissors. If someone overindexes on speed they'll do no damage and have too little defense. This is fine in parties if we have someone picking off the weaklings." And of a long channel: "his next one should probably oneshot someone lol." The design wrote twelve bounds before any run (section 6). The rules are now real code (`fight.ts` and what it calls). This unit plays them and shows whether the numbers hold, and moves a number only by its named lever, with the reason written down. No screen changes until these hold.

## Steps

1. **The player.** `tests/models/fight-sim.ts`: the five builds of design section 2 (speed, tank, cannon, bruiser, support) at E, C and S as `Build` values (one table, a class adds a row), each with the two or three abilities its archetype uses made from `abilityOf` (a default attack, and its signature: the cannon's mana blast, the tank's taunt, the support's shield, a channel for the cannon), and one policy per archetype written as a short pure function from the fight to a command (who to target, when to move, when to use the signature, when to channel): plain and readable, the play of a sensible player, not an optimizer. Monsters use the threat table's suggested target and their kind's default ability. Dice come from the seeded `rng`. `playFight(setup, seed)` drives the real `reduce` until the fight ends or a time cap, failing loudly on any `refused` effect it did not expect. Commit with a smoke test (one fight of each row ends).
2. **The rows.** `tests/fight-sim.test.ts`: one row per bound of design section 6, read from a table in the test file (`{ name, setup, runs, measure, low, high, lever }`), so a new class or bound is a new row (model-the-domain). Before any run, write in the file's header the noise floor you will accept: choose `runs` so the standard error of each share is under 2.5 points (say the arithmetic), and print for each row the measured value, its standard error and whether it is inside the bound. The whole file should run in under about 20 seconds so it stays in `bun run test`; if it cannot, say what bounds the time and reduce `runs` only as far as the noise floor allows. First run: every row prints, and rows outside their bound are listed in `docs/agent-handoff/rw/sim-log.md` with the measured value. Do not tune yet. Commit the player and the rows with the out-of-bound rows marked `test.todo` with the measured number in the name (they become real tests in step 4).
3. **Explain the numbers** before changing any. For each row outside its bound, and for the three rows closest to an edge, write in `sim-log.md` what limits it (which build runs out of what, who acts how many times, how much of the damage is avoided, absorbed or reduced: add counters to the player's output, not to core) and rule out the other things it could be measuring: a policy that plays the build badly, a fight that hits the time cap, a refused command, a one-sided opening distance. If a row misses because the policy is poor, fix the policy and say so. If two changes to the same lever fail the same bound, stop and write down the premise they share before a third (attack-the-premise). Commit the log.
4. **Tune, one lever at a time**, in the design's order: speed (turn rate and the reaction edge), then defence (Armor and Resist and penetration), then resources (fatigue back per fight, mana), then the extras (channel hold and growth, stagger size, shields, threat and taunt). For each change: the row, the lever (a number in `RULES.fight`), the old and new value, the reason in a sentence a GM could read, the row's value before and after, and every other row re-measured (a change that fixes one row and breaks another is not accepted). Update the number's comment in `rules.ts`, the paper script's output if it prints it, and the literal in any unit test whose expected value came from the design's table for that number (the design's table changes with it: edit `design.md` to the new number and reason). Turn each `test.todo` into a real test as its row comes inside. One commit per accepted change. If a bound itself is wrong (the design's reason for it does not survive what the simulation shows), do not move it quietly: say so in `sim-log.md` under "Bounds I would change", with the evidence, and leave its row `todo`.
5. **What the table cannot show.** At the end of `sim-log.md`, at most half a page: which numbers the simulation is insensitive to (move them 20 per cent and say what moved), which rest on the policy more than on the rules, and the three things to watch in a real session.
6. **Check and notes.** `bun run typecheck`, `bun run test`, `bun scripts/rw-paper.ts`, `bun run deps -- --write` (commit what it changes). `docs/agent-handoff/rw/notes-u5.md`: the final table of rows (value, standard error, bound, lever), every number changed with old, new and reason, the rows still `todo` and why, any bug in `fight.ts` or the rule modules the simulation found (fix it at its root with a test in that module's own test file, one commit each, and list it), the exact last line of `bun run test`.

## Rules

- The simulation calls the real `reduce` for every change to the fight. No rule is reimplemented in the player.
- A balance number changes only in `RULES.fight`, one at a time, with its reason. No special case for an archetype in core.
- A bound is not loosened to make a row pass.
- Report run count and spread with every number.
- Plain whole sentences in the log and notes; a GM should be able to read `sim-log.md`.

## Done means

`tests/fight-sim.test.ts` in `bun run test` with every row inside its bound or `todo` with its reason; `sim-log.md` and the notes; typecheck and `bun run test` green; the tree clean.
