# The Hunter System: guide for coding agents

A phone-first tabletop RPG companion. A GM phone and player phones share a room. Served by `bun server.ts`.

This file is the single guide for any coding agent. It grows as the architecture pass lands. Keep it short and true.

## Set up once

```
bun install
bunx playwright install chromium
git config core.hooksPath .githooks
```

The last line turns on the pre-push hook. Without it, pushes are not checked.

On a machine that ships its own Chromium (a cloud box), skip the Playwright install and set `E2E_CHROMIUM` to that browser's path for every Playwright or CI run. Set it also where Playwright's default headless shell refuses notifications (`tests/e2e/used.e2e.ts`, "a GM who allowed notifications", then reads "Blocked in this browser's settings"): point it at a full browser, the machine's own (`/opt/google/chrome/chrome` on the cloud box) or the Chromium Playwright installed beside the shell (`~/.cache/ms-playwright/chromium-*/chrome-linux/chrome`).

## Run, test, check

| What | Command |
|---|---|
| Run the app | `bun start` (port 3000). The server bundles the app once at start, so restart it after a change |
| Build for a static host | `bun run build` (writes `dist/`) |
| Typecheck | `bun run typecheck` |
| Typecheck, unit tests and lint checks | `bun run test` |
| One browser test file | `bunx playwright test tests/e2e/<file> --workers=1 --output=/tmp/pw-<name>` (starts its own server on 3217; set `E2E_PORT` when two runs overlap) |
| Everything a push must pass | `bun run ci` |
| The room API against Postgres, the store the deploy uses | `DATABASE_URL=postgres://... bun test tests/server-rooms.test.ts tests/server-handshake.test.ts` (an empty database; without the variable the same tests use the memory store) |
| Redraw the state charts | `bun run charts` (writes `docs/state-machines.md`) |

## Layout

```
src/app.js     entry: view registry, routing, header. Lists every module it registers
src/core/      pure logic. No DOM, no storage, no network, no imports from edge or views
src/edge/      the store (localStorage), the room link and its pill (network), edge/rules.ts (the current rules for views), edge/roll.ts (every die a fight asks for)
src/views/     DOM modules, one per screen or panel
src/sw.js      service worker source
public/        files served as they are (index.html, app.css, manifest, icons)
scripts/build.ts   bundles src/ and public/. The build id is a hash of the inputs
server.ts      serves the built files and the room API
```

## Recipes

Where a step says "the typecheck asks", `bun run typecheck` fails until it is done.

- A combat command: a member of `Command` (`src/core/combat/fight-types.ts`) and its cell in every row of `TABLE` in `src/core/combat/fight.ts` (the typecheck asks; `null` where it does not apply). Return a new fight; refuse with a `refused` effect, never throw; a new `Refusal` gets its words in `src/core/combat/refusal-words.ts` (the GM's, and a player's when it is in `TABLE_REFUSALS`; the typecheck asks). A log line is `logged(f, line(text, rows, zones), R)`, naming every row and zone its words are about. Dice arrive inside the command: the view asks `needs` (`resolve.ts`) and rolls with `src/edge/roll.ts`. What reaches outside the fight is an effect (`Fx` in `fight-types.ts`): one that writes the save is a line of `fought` (`fight-save.ts`), the rest carried out by `send()` in `combat.js`; a hunter's sheet hears of its row only through `writeBack` (`fight-turn.ts`): the `vitals` effect, a remote's `sendRemote`, a shadow's `shadowHp`. A test in `tests/fight.test.ts`, the command in `randomCommand` (`tests/models/fight-play.ts`), and its words in `step` in `scripts/charts/fight.ts`.
- An ability: an entry with its kind (strike, shot, blast, curse, support), made by `abilityOf` (`src/core/registry/ability-kinds.ts`), which fills cost, range, shape, delivery and the kind's recommended formula; give only what differs. A built-in is an entry in `SKILL_ABILITIES` or a seed's `MonsterSpec` (`src/core/registry/abilities.ts`); `tests/abilities.test.ts` checks every one parses and stays inside design section 6's single-hit bound. A new kind is a member of `AbilityKind`, its row in `KINDS` and its numbers in `RULES.fight.abilityKinds` (the typecheck asks).
- A shape: a member of `Shape` and its case in `tilesOf` (`src/core/combat/space.ts`; the typecheck asks), with a case in `tests/space.test.ts`. `aims` (`fight-view.ts`) and `resolve` then read it with no change.
- A terrain: a member of `Terrain` and its row in `TERRAIN` (`space.ts`: its character, whether a body may stand on it, its cost to enter, whether it stops a line and sight, whether it is cover; the typecheck asks), with a case in `tests/space.test.ts` on a drawn grid. Nothing else: `cardDesc` passes every number of `Card` to the template, and `bind` writes it when it changes. A word or control that is not a fight number is a field `cardDesc` adds. A list or something that comes and goes is a `data-part` (markup, rewritten whole when it changes) and holds no binding of its own.
- A motion: call a move from `src/views/motion.ts` after the view draws (`enter`, `dismiss`, `pop`, `shake`, `flash`, `fadeOff`, `slideTo`, `fillTo`, `numberTo`, `tumble`, `burst`, `progress`); never await one before a command. A time or an easing is a token on `:root` in `public/app.css`, a new move a function in `motion.ts` built on `play` (only `transform` and `opacity`), a burst kind a row of `BURSTS`. A view writes no time, no `@keyframes` and no `.animate(` (the lint tests ask). After a change to a fight screen, run `tests/e2e/feel.e2e.ts`.
- More info on a thing: a new kind is a member of `Thing` and its case in `detailOf` (`src/core/detail.ts`; the typecheck asks), with a case in `tests/detail.test.ts`, its lines from core's own sentence functions. A view puts `app.api.detail.control(list, key)` on the thing's button, `app.api.detail.panel(list, key, thing)` right after it in its markup, and calls `app.api.detail.wire(root, redraw)` once; the open one is kept by the component, so a view that redraws draws it open again. A sentence goes in core, never in the view.
- An event: its entry in `AppEvents` (`src/core/events.ts`), then `app.emit` and `app.on`. An API member: its type in `src/core/api.ts`, its registration in the module, and a caller in another module.

Each content table has a test that checks every entry, so new content needs no new test: run `bun run test`. After a change to imports, `app.api`, events, views or panels, run `bun run deps -- --write`; after one to a machine, `bun run charts`. A new module with a `register(app)` is imported and listed in `MODULES` in `src/app.js`. Only what the build produced is served: a new static file goes in `public/`.

## Saves and roles

A save has `schema: 4` under `hunter-system-v4`. A tab whose stored save a newer app wrote, or whose unsaved change another tab's save overtook, is read-only: `store.apply` refuses every change (`read-only`) and a banner says why; a restore, an import or a reset makes it ready again. An older save (schema 1 to 3, under `hunter-system-v3`, `-v2` or `-v1`) is not carried over: its text is kept in the backups, the player is told, and the app starts a new campaign; its old key is left as it was. A campaign file or a hunter from before schema 4 is refused at import. A stored text that is not a save is kept in the backups and the player is told. In a room the phone that holds the room's GM key is the GM; `settings.mode` is only what a phone chose while alone.

## Finding what depends on what

`AppEvents` in `src/core/events.ts` and `AppApi` in `src/core/api.ts` are the two typed tables between modules. `tsconfig.views.json` checks the views as loose JavaScript against the `App` of `src/views/app.ts` (no null checks); a choice read from the page goes through `oneOf` in `src/core/one-of.ts`. `docs/dependency-map.md` lists each file's imports, API members, events, save keys, views and panels; `bun run deps -- <name>` prints one entry (a file, an API, a member such as `combat.add`, or an event). The map follows literal event names and `app.api.<name>.<member>` or a declared alias (`const A = () => app.api`).

## Machines and their charts

`docs/state-machines.md` charts every explicit machine: the fight and a channel (`fight.ts`, `fight-channel.ts`), a stacking status's count (`stacks.ts`), a trigger's limit (`triggers.ts`), a delayed effect (`delayed.ts`), a zone of the kits (`zones.ts`), a timed summon (`summons.ts`), a limited use (`uses.ts`), wave 2's reaction, edge, push, stealth, ward and turn extras (`fight-react.ts`, `standing.ts`, `space.ts`, `timeline.ts`; one file of views, `scripts/charts/wave2.ts`), a gate, the room link, a hunter's life, the penalty, the Job Change chain and a coin call (`coin.ts`), first-run setup (`onboarding.ts`), a gesture on the battle map (`combat/gesture.ts`) and what the map has chosen (`choose`, `map-view.ts`), a shadow (`hunter/shadows.ts`) and a corpse's extraction (`combat/extraction.ts`), a quest (`hunter/quests.ts`), the room server's database (`room-server.ts`) and the app update (`upgrade.ts`), a message in the outbox (`sync/outbox.ts`), the store's life (`store-life.ts`), a run of the odds engine (`combat/odds.ts`), a hunter's personal gates (`gates/solo.ts` `soloTick`) and a solo run waiting for the GM (`gates/solo-wait.ts`). `bun run charts` walks the real reducers with the event lists in `tests/models/` (the fight has no end of states, so its chart replays the random play of `tests/models/fight-play.ts`), and `tests/statecharts.test.ts` fails when the file is stale or a state has no box. ## Build handshake

Every `/api/rooms...` request carries the build id in `X-Hunter-Build`; the server answers another build with `426 { error: 'upgrade', build }` and the app reloads once, after the new build's service worker has cached every file and taken over, or at once when none installs (the app update's machine in `src/core/upgrade.ts`, run by `src/edge/upgrade.ts`). A change to the room wire format needs no version number. A test that calls the room API sends the header: `roomHeaders(page)` in `tests/e2e/helpers.ts`, or `buildApp()` in a bun test (`tests/server-handshake.test.ts`).

## CI is local

`bun run ci` (`scripts/ci.ts`) runs the typecheck, `bun test` and every Playwright test against its own server on port 3218, the lag test (`tests/e2e/feel.e2e.ts`) last in a pass of its own with one worker, because it times frames and must have the machine to itself. The pre-push hook runs it and blocks a push that fails or has uncommitted files. A push runs only the passes it can change: the hook hands the CI the files the push changes, and `planOf` in `scripts/ci-plan.ts` decides (`tests/ci-plan.test.ts`). The typecheck and the unit tests always run. A push of only the lead's notes (`docs/agent-handoff/`), unit tests and their models, chart scripts, the generated docs, this guide or the CI's own scripts runs no browser test; a push that changes browser test files and not the app runs those files alone (the lag test only if it is one of them); anything a browser test can see (`src/`, `public/`, `server.ts`, the build, `tests/e2e/helpers.ts`, `tests/fixtures/`, the config, the package), a new branch or a file the plan does not know runs everything. A new kind of file that no browser test can see gets a line in `isUnitOnly` with its reason. `bun run ci` by hand runs everything. "CI green" means `bun run ci` passed on the commit being pushed. A step that failed across a pause of the box is rerun once; a failure without a pause never is.

## Tests

- `tests/*.test.ts`: bun tests of pure logic and the server handler in process. Copy `tests/server-rooms.test.ts`.
- `tests/e2e/*.e2e.ts`: Playwright on phone viewports. Copy `tests/e2e/room-sync.e2e.ts` and import from `tests/e2e/helpers.ts`; `device()` fails a test on any console error.
- Test names say what a player or GM sees. Drive the action under test through the UI; use the store only for setup and reading.
- `device()` opens every phone of a test in a zone where the test's start is noon (`noonZone` in `helpers.ts`), so no test meets the day's reset by the hour it runs; a test about the day's clock names its zone with `timezoneId`.
- No retries and no fixed waits to hide a race. Wait for a window by its title before tapping past it; `E2E_POPUP_DELAY=100` opens every window 100 ms late to find a test that does not.
- A hunter alone gets a personal gate on open, and its "A GATE HAS APPEARED" window stands over the page. `onboardPlayer` answers it; a test seeded from a save whose subject is not the gate sets `rulesOverrides.solo = { personal: false }` in its setup.
- A won fight, a cleared gate, a solo run or a daily can earn a feat, and its window ("! Feat", as "NO PARTY WAS NEEDED" after a player's first gate cleared alone) queues after the thing's own window and stands in front of the next one a test waits for. A test whose subject is not the feat turns feats off in its setup: `rulesOverrides.feats = { on: false }` (in a room, on the GM's phone, and wait for the player's `hunterApp.rules().feats.on` to be false), as `tests/e2e/solo.e2e.ts` does.
- `page.route` does not see a request a service worker makes. A test that holds or fails `/api` with it opens its device with `blockServiceWorker: true`.

## Rules

- Dev dependencies are `typescript` and `@playwright/test` only. No CDN, no `@types/*`; ambient types are in `types/`.
- TypeScript is strict. New core code is `.ts`.
- The lint rules are the tests in `tests/lint.test.ts`: each test's name is the rule, and its comment or message says why and what to do instead. They keep `src/core` pure (no edge or view imports, no browser API, no module-level `let`), give each piece of state one writer (the role, a gate's status, the fight, a combatant's place, HP, shield, stagger, channel, threat and statuses, room event ids, the save's room fields, a hunter's progress, vitals, penalty and chain, a quest's end time, the coin calls), give an item and a monster one parser each, keep the GM's statuses out of the rule overrides, keep the fight's numbers in core (a view rolls no fight die and computes no fight number; a balance number is a rule in `RULES.fight`, not a literal), keep the deleted old fight deleted, keep every module of `src/edge` to the state the lint names with what it holds (sync.ts's at its top too), let a view write the save only through `store.apply` with a step from core, keep the day's clock in `src/core/day.ts`, name each timer a view sets with its reason, let a view ask `app.seat()` whether the phone is in a room and as what, let only `src/edge/upgrade.ts` listen to the service worker, keep the browser's storage in `src/edge/store.ts` (`store.device` for a view's memory), keep `server.ts` without room state of its own and without `any`, let no catch in `src/` or `server.ts` swallow its error, name each `let` and each Map, Set, list or object a view keeps for the page (none holds a row's, a hunter's or a saved thing's state), and give each exported type name one meaning (no list of exceptions). When a bug class shows up twice, add a test there.
